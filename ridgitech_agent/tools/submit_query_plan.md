# submit_query_plan

Проверяет и регистрирует план. Самостоятельно не загружает данные и не считает итог.

Передай `plan`, когда определены метрика, организация, даты и разрезы, проверена
схема и разрешена неоднозначность. Используй версии из `get_metric_definition`.
Точный формат аргументов дан в JSON Schema этого tool; не добавляй поля,
которых в ней нет, даже если они предусмотрены целевой архитектурой.

Текущий каркас принимает `metric_id`, `semantic_version`, `catalog_version`,
`organization_id`, `period` с `start/end_exclusive` и `group_by`. Это шаблон суммы
за период. Не пытайся выразить им остаток на момент, top-N, сравнение периодов
или произвольный фильтр. Для них нужны отдельные поддержанные шаблоны.

Источник, поля, обязательные фильтры и формулу добавляет сервер из определения
метрики. URL, права и ограничения задаёт backend; менять их через plan нельзя.

При успехе получишь `status=accepted` и `plan_id`. Заверши планирование:
дальше оркестратор запускает Executor. Не придумывай числовой ответ.
При ошибке исправь её причину в рамках бюджета попыток. Для `STALE_PLAN`
обнови определение; при недостающих пользовательских параметрах задай вопрос.
Не повторяй неизменённый невалидный план бесконечно и не запускай второй расчёт
повторной отправкой принятого плана.

Основание: ФТ-3.1–3.7 и ФТ-4.1–4.2 ТЗ.
