# Базовые tools AI-агента

Агент работает как граф LangGraph. LangChain связывает локальную LLM с типизированными
инструментами. Модель понимает вопрос и составляет план, валидатор проверяет его,
а ToolNode обращается к API данных. Расчёты, пагинация, связи и доступ к штатному
OData 1С находятся в слое данных.

![Архитектура агента](architecture.png)

## Стек и модели

Python 3.12, FastAPI, LangGraph StateGraph, LangChain, Pydantic, HTTPX,
PostgreSQL для истории, аудита и checkpoints, Redis для кэша с TTL.
Локальный инференс - vLLM; для LLM-трейсов и оценки качества - self-hosted
Langfuse, для технической наблюдаемости - OpenTelemetry.

Варианты LLM: **Qwen3.8-27B** и **DeepSeek-V4-Flash**. Для Qwen используется
`Qwen/Qwen3.8-27B`; у DeepSeek рассматривается релиз
`deepseek-ai/DeepSeek-V4-Flash-0731`. Версии весов, шаблона чата и парсера tools
фиксируются вместе. Между моделями выбираем по качеству на вопросах про продажи,
поступления, взаиморасчёты, даты и уточнения, а также по задержке ответа.

## Устройство графа

1. **Контекст и каталог** - загрузить историю, права, выбранную базу, время и
   релевантные определения из каталога 27 опубликованных наборов.
2. **Планировщик** - выбрать метрику и инструменты, разрешить названия организаций
   и направлений, сформировать конкретные даты и план.
3. **Валидация** - проверить JSON Schema, доступы, обязательные параметры,
   версии определений, зависимости шагов и бюджет выполнения.
4. **Уточнение** - при нехватке контекста приостановить граф через interrupt;
   после ответа пользователя продолжить через resume с обновлённым контекстом.
5. **ToolNode** - выполнить разрешённые операции плана через адаптер API данных.
   Результаты подготовительных инструментов возвращаются планировщику.
6. **Проверка результата** - проверить полноту, валюту и единицы, период,
   применённые фильтры, источники и контрольные правила метрики.
7. **Ответ** - собрать число/таблицу и объяснение расчёта; передать результат в чат.

Состояние графа содержит сообщения, разрешённый контекст, найденные метрики,
недостающие параметры, план, результаты шагов, источники, предупреждения и счётчики
попыток. Checkpoints сохраняются в PostgreSQL. Пароли и большие выгрузки остаются
за пределами состояния и промпта. Ключ выполнения учитывает базу и запрос;
повторная доставка шага использует сохранённый результат по ключу идемпотентности.

## Общий контракт

Имена ниже - интерфейсы агента. Адаптер связывает их с методами API данных.
Для каждого инструмента предусмотрены Markdown-инструкция, JSON Schema аргументов
и обработчик LangChain. База, права, учётные данные, лимиты и deadline
поступают из доверенного контекста backend.

Успех возвращается как `ok + data + sources + warnings + stats`.
Для числовых результатов указываются единица, период/момент, организация,
фактические фильтры, версия определения и время получения данных.
Деньги передаются десятичными строками. Ошибка содержит `code`, `message`
и признак возможности повтора.

### 1. `search_metrics(query)`

**Назначение:** найти метрику по бизнес-вопросу и русским синонимам.

**Вход:** `query` - вопрос либо описание показателя.

**Выход:** кандидаты с `metric_id`, названием, смыслом, статусом определения
и поддержанными операциями.

**Инструкция:** начинай с этого инструмента. Сравни смысл кандидатов, затем получи
полное определение. При нескольких подходящих трактовках уточни выбор.
Различай выручку, продажи, поступления и оборот.

### 2. `get_metric_definition(metric_id)`

**Назначение:** получить согласованную методологию расчёта.

**Вход:** `metric_id` из каталога.

**Выход:** источник истины, формула, единица/валюта, обязательные фильтры,
параметры времени, разрезы и операции, правила знака/округления, связи и версия.

**Инструкция:** используй определение перед составлением плана. Сохраняй обязательные
условия. Для остатков выбирай согласованную виртуальную таблицу, для оборотов -
соответствующее определение периода. Неподтверждённая методология требует согласования.

### 3. `get_entity_schema(entity_name)`

**Назначение:** получить описание опубликованного источника и его возможностей.

**Вход:** `entity_name` из определения метрики.

**Выход:** поля, типы, ключи, связи, функции, параметры виртуальных таблиц,
карта `$expand`/client-side join и версия каталога.

**Инструкция:** проверяй источник перед первым использованием и при смене версии.
Планируй запрос по указанным возможностям. Раскрытие связей и получение страниц
делегируй слою данных.

### 4. `resolve_dimension(dimension, query)`

**Назначение:** превратить название из вопроса в идентификатор параметра.

**Вход:** разрешённое `dimension` (`organization`, `counterparty`, `direction`)
и `query` - название или его фрагмент.

**Выход:** доступные кандидаты с идентификатором, названием и признаками для различения.

**Инструкция:** используй для объектов, названных текстом. При нескольких совпадениях
уточни выбор. Передавай в расчёт идентификатор выбранного объекта.

### 5. `submit_query_plan(plan)`

**Назначение:** проверить и зарегистрировать план перед расчётом.

**Вход:** метрика и версия определения, организация, период либо момент среза,
разрешённые фильтры, форма ответа и шаги. У шага есть `step_id`, имя расчётного
инструмента, типизированные аргументы и зависимости `depends_on`.

**Выход:** принятый `plan_id` и нормализованный план либо структурированные ошибки.

**Инструкция:** вызывай после разрешения смысла и параметров вопроса. Исправляй
конкретные ошибки в пределах бюджета. После принятия передай управление графу.
Расчёт запускает ToolNode; повторная подача плана не создаёт второй расчёт.

### 6. `get_sales_turnovers(...)`

**Назначение:** получить обороты продаж за период.

**Вход:** `metric_id`, `period`, `organization_id`, разрешённые `group_by` и `filters`.

**Выход:** итоги/таблица оборотов, единица/валюта, источники, условия расчёта и полнота.

**Инструкция:** используй для вопросов про продажи по согласованной методологии.
Группировки и фильтры бери из определения метрики. Итог используй из API.

### 7. `get_top_counterparties(...)`

**Назначение:** получить рейтинг контрагентов по согласованному показателю оборота.

**Вход:** `metric_id`, `period`, `organization_id`, `limit`, разрешённые `filters`.

**Выход:** упорядоченная таблица контрагентов со значением, позицией, единицей и источниками.

**Инструкция:** уточни трактовку оборота и период, если они неоднозначны.
Рейтинг строится по всей выборке после фильтрации и агрегации;
размер результата `limit` отличается от лимита исходной выгрузки.

### 8. `get_cash_receipts_by_direction(...)`

**Назначение:** получить поступления денежных средств по направлению.

**Вход:** `metric_id`, `period`, `organization_id`, `direction_id`, разрешённые фильтры.

**Выход:** сумма/таблица поступлений, единица/валюта, направление, условия, источники и статистика.

**Инструкция:** разреши название направления в идентификатор. Следуй определению
поступлений, включая правила проведения и возвратов. Различай поступления и выручку.

### 9. `get_customer_balances(...)`

**Назначение:** получить остатки взаиморасчётов с покупателями на момент времени.

**Вход:** `metric_id`, `as_of`, `organization_id`, при необходимости `counterparty_ids`
и разрешённые разрезы.

**Выход:** остатки, единица/валюта, момент среза, источники и правила трактовки знака.

**Инструкция:** используй для остатков и задолженности покупателей по выбранному
определению. «На сегодня» конкретизируй по временной зоне и методологии среза.
Отрицательный остаток трактуй по определению метрики.

## Правила исполнения

- Подготовительные tools 1-4 доступны планировщику. Tool 5 фиксирует проверенный план.
  Расчётные tools 6-9 выполняются ToolNode только по принятому плану.
- Независимые шаги допускают ограниченный параллелизм; зависимые выполняются
  после получения входных результатов. Ограничения нагрузки действуют на базу.
- В API данных находятся пагинация, `$expand`, пакетный join, Decimal-агрегации
  и кэш полных промежуточных выгрузок с TTL. При отсутствии `$apply` суммы
  и группировки считаются сервисом данных.
- Относительные даты разрешаются по времени backend и правилам границ метрики.
  Остаток на момент и оборот за период имеют разные параметры.
- Пустая выборка сопровождается предупреждением. Лимит или незавершённая выгрузка
  завершаются понятной ошибкой с предложением сузить запрос.
- Исправления плана, повторы вызовов и генерация LLM расходуют общий бюджет.
  Уточнение сохраняет состояние; при resume доступы и бюджет проверяются заново.
- Ответ содержит точные значения из API, время, организацию, источники, предупреждения
  и объяснение. Сравнение периодов использует проверенные шаги и арифметику кода.
- Аудит фиксирует версии модели, промпта, схем tools, каталога и методологии,
  аргументы шагов, объём данных, время, ошибки и источники.
