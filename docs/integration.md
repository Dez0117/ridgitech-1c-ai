# Стыковка агентного модуля

## Никите: интерфейс

Маршруты из схемы можно сохранить. Агент не поднимает второй FastAPI
и не пишет напрямую в таблицы диалогов.

```python
result = agent.run(question, conversation_context, execution_context)
payload = result.model_dump(mode="json")
```

`conversation_context` — текст, а не сообщения с произвольными system-ролями.
Backend создаёт `ExecutionContext` из авторизованного подключения/прав,
а не копирует его из пользовательского запроса:

- `request_id`, `base_id`, `allowed_metric_ids`, `allowed_organization_ids`;
- `current_date` как `date`, `timezone` выбранной базы;
- `limits` (включая общий бюджет до 60 секунд);
- `demo_mode=False`; `True` только для тестового каталога.

`Agent(catalog, adapter, model)` получает выбранные backend зависимости.
Каталог, адаптер и контекст относятся к одной базе. `Tools` создаётся на каждый
запрос; изменяемое состояние модельных/данных адаптеров не разделяется между запросами.
Инструкции каждого tool лежат рядом с его кодом в `ridgitech_agent/tools/`.
Реестр загружает их из `.md` и публикует функции модели; пути к файлам в промпт
передавать не нужно. Системный промпт загружается из `ridgitech_agent/prompts/system.md`.
Метод синхронный: FastAPI запускает его через thread pool или worker.
Надёжное выполнение после перезапуска требует очереди и сохранённого состояния;
конкретную библиотеку очередей за backend эта архитектура не выбирает.

Предлагаемый HTTP-контракт:

1. `POST /api/v1/conversations/{id}/messages` сохраняет сообщение, создаёт запрос,
   возвращает `202` и `request_id`.
2. `GET /api/v1/requests/{id}` отдаёт `queued/running`, затем результат агента.
   `needs_clarification` завершает текущую обработку и ожидает нового сообщения.
3. Уточнение получает новый request ID и историю предыдущего вопроса.
   Авторизация диалога/запроса проверяется при каждом обращении.
4. План и trace сохраняются для «Как посчитано»; UI получает разрешённую проекцию
   аудита. Стадия и количество прочитанных страниц для прогресса — следующий шаг
   на уровне worker, в текущем агенте callback прогресса отсутствует.

Повтор одного POST дедуплицируется в БД по пользователю/диалогу и client message ID.
Хеш `plan_id` этого не заменяет.

| Поле результата | Назначение |
|---|---|
| `status/message` | `completed`, `needs_clarification`, `failed`; текст для чата |
| `data` | Таблица; деньги строками (`"4000.00"`), без float |
| `query_plan` | ExecutionPlan с исходным QueryPlan и реальными фильтрами |
| `sources/warnings` | Источники и ограничения; предупреждение о демо показывать обязательно |
| `stats/trace` | Статистика и детали для аудита |
| `error` | Машинный код и безопасное сообщение либо null |

Основные коды: `INVALID_ARGUMENTS`, `ACCESS_DENIED`, `STALE_PLAN`,
`UNAPPROVED_METRIC`, `SOURCE_NOT_AVAILABLE`, `UNSUPPORTED_METRIC`, `INVALID_PLAN`,
`PLAN_ALREADY_ACCEPTED`, `MODEL_PROTOCOL`, `MODEL_UNAVAILABLE`, `MODEL_BUDGET`,
`TOOL_BUDGET`, `ROW_LIMIT`, `PAGE_LIMIT`, `TIMEOUT`, `INVALID_DATA`,
`INCOMPLETE_DATA`, `UPSTREAM_UNAVAILABLE`.
Ошибки подключения не раскрывают секреты/внутренние адреса. Непредвиденные
программные исключения обрабатывает error handler backend.

## Григорию: входные данные

Для первого реального сценария нужен один согласованный вопрос и метрика
с проверенным определением и контрольным ответом:

| Материал | Содержание |
|---|---|
| Схема | EDMX, версия платформы и состав публикации; секреты отдельно |
| Метрика | Источник истины, поля, единица/валюта, период/момент, обязательные фильтры, знак/округление |
| Контекст | Ключи организаций, временная зона базы |
| Связи | Expand paths; для исключений — ключи, типы, кардинальность join |
| Контроль | Вопрос, параметры, контрольная сумма/таблица, источник ручной сверки |
| Методология | Согласование заказчиком до статуса approved |

Тестовая карточка: `ridgitech_agent/fixtures/catalog.json`. Сейчас поддерживаются
одна коллекция, sum и строковые разрезы. Для Balance/Turnovers сначала вводим
отдельный тип источника с параметрами виртуальной таблицы и его валидацию.

Точка чтения — `DataAdapter` в `ridgitech_agent/executor.py`:

```python
class DataAdapter(Protocol):
    base_id: str

    def read_page(self, read, *, top: int, skip: int, timeout: float) -> Page:
        ...
```

Адаптер применяет фильтры и стабильную сортировку до `$top/$skip`, возвращает
нормализованные строки и достоверный `has_more`. Decimal декодируется без float,
даты нормализуются к согласованному представлению времени базы. Реальное чтение
потребует типов GUID, составных ключей и формата дат v3 — тестовый строковый
ключ этого не моделирует.

`odata_parameters` строит preview для поддержанных типов, но не является
HTTP-клиентом. URL/Basic Auth задаются доверенной конфигурацией. Реальные next links
не должны уводить клиента на другой хост/публикацию. Отсутствие регистра,
отказ в доступе и сетевой сбой различаются и не превращаются в пустую выборку.

## Следующая итерация

1. Выбрать один вопрос и подтвердить определение метрики с заказчиком.
2. Получить от Григория схему/правила; Санан обновляет каталог и шаблон плана.
   Команда отдельно назначает владельца промышленного OData-адаптера.
3. Подключить GET-чтение и сверить пагинацию/точность на контрольном периоде.
4. Никита подключает `Agent.run`, хранение результата и опрос статуса.
5. Проверить уточнение, неоднозначность, недоступную 1С, пустую выборку, лимиты,
   повторы. Качество выбранной LLM проверяется на согласованных русских вопросах:
   тесты со сценарной моделью этого не измеряют.
6. Добавить промежуточный кэш и нагрузочную проверку перед рабочим запуском.

Санан: планировщик, tools, контракты, ответы. Григорий: фактическая схема, источники,
связи, методология вместе с заказчиком. Никита: HTTP, авторизация, фоновые запросы,
хранение, инфраструктура. Metadata Scanner, OData Executor и семантическое
хранилище затрагивают несколько зон; владельцев их реализации нужно зафиксировать.
