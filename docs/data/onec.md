# Подключение 1С


Реализован один реальный сценарий: сумма поступлений за период по одной организации и одному направлению. Остальные бизнес-инструменты пока доступны только в синтетическом источнике.

## Устройство

`AgentService → OneCDataBackend → HTTP /v1/call → OneCDataService → OData GET`.

`ANALYTICS_BACKEND=fixture` сохраняет прежнее поведение. При `ANALYTICS_BACKEND=onec` worker получает контекст из `/v1/bootstrap` и использует HTTP-адаптер. История, очередь и хранение результатов остаются в существующем backend.

Внутренний сервис предоставляет:

- `GET /health` — проверка процесса, без обращения к 1С;
- `GET /v1/bootstrap` — доступные организации и направления с настоящими UUID, разрешённые источники и определение метрики;
- `GET /v1/bootstrap?refresh=true` — принудительное обновление схемы и справочников с той же проверкой внутреннего токена;
- `POST /v1/call` — четыре подготовительные операции и `get_cash_receipts_by_direction`;
- `GET /docs` — документация HTTP API.

## Локальный запуск

Из корня репозитория:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -e '.[backend,test]'
.venv/bin/python -m services.onec_data
```

Пароль пользователя OData вводится скрыто и не сохраняется. Используются настройки `ODATA_BASE_URL` и `ODATA_USERNAME`; для предоставленной демобазы в локальном запуске они заданы по умолчанию. Локальный сервер слушает `127.0.0.1:8011`.

В другом терминале:

```bash
cd /Users/grigorii_zorinov/Desktop/Repos/ridgitech-1c-ai
curl -sS http://127.0.0.1:8011/v1/bootstrap | python3 -m json.tool --no-ensure-ascii
.venv/bin/python scripts/check_onec.py --allow-demo
```

Проверка получает данные через адаптер напрямую, затем через инструменты и граф агента, затем через `AgentService`. Сравниваются результаты всех трёх путей. В роли планировщика используется контрольный план; внешняя LLM не вызывается. Это проверка интеграции данных, а не качества понимания русского вопроса.

При необходимости можно выбрать другую выборку:

```bash
.venv/bin/python scripts/check_onec.py --allow-demo \
  --start 2025-01-01 --end-exclusive 2025-02-01 \
  --direction 'Разработка ПО' --organization '<UUID из bootstrap>'
```

Если задан `ONEC_DATA_TOKEN`, передавайте его в `X-Internal-Token` при ручных HTTP-запросах. Адаптер и проверочный скрипт читают его из переменной окружения.

## Методика и внутренняя модель

Источник — `AccumulationRegister_ДвиженияДенежныхСредств_RecordType`. Одна строка означает движение регистра; уникальность задают ключи, прочитанные из `$metadata` (в демобазе — регистратор, его тип и номер строки). Данные сгруппированного отчёта не смешиваются с первичными движениями.

Обязательные фильтры:

1. `Period >= start 00:00:00` и `Period < end_exclusive 00:00:00`;
2. точные `Организация_Key` и `НаправлениеДеятельности_Key`;
3. `Active = true`;
4. `ВидДвиженияДС = 'Поступление'`.

Названия разрешаются через справочники организаций, направлений и контрагентов. Bootstrap загружает только организации и направления; поиск контрагентов отправляет в 1С фильтр по UUID либо подстроке имени без учёта регистра. Читается ограниченное число кандидатов и одна контрольная строка; при усечении возвращается предупреждение об уточнении запроса. Размер или отсутствие этого справочника в публикации не блокируют расчёт поступлений. Для расчёта используются UUID. Произвольный URL или текст OData-фильтра из аргументов агента не принимается. Поле `Active` относится к движению регистра; его нельзя без проверки подменять признаком `Posted` документа.

Поток: проверка контекста и аргументов → разрешение идентификаторов → типизированный план чтения → проверка по `$metadata` и формирование OData → последовательные страницы с сортировкой по всем ключам → повторная проверка периода и фильтров каждой страницы → сложение `Сумма` через `Decimal` → округление `ROUND_HALF_UP` до двух знаков → `BackendResult`.

Расчёт обрабатывает страницы через `iter_pages`, без накопления всех денежных строк. Между страницами сохраняются сумма и ключи для проверки дублей. При ошибке любой страницы результат с частичной суммой не возвращается. Метод `rows` оставлен для небольших справочников и существующего сборщика эталонов.

Деньги возвращаются десятичными строками. Пустая выборка возвращает `rows=[]`, `total=null` и предупреждение. Превышение лимита, повтор страницы, дублирование ключа, некорректные деньги и неполная выгрузка приводят к ошибке без частичной суммы. `complete=true` означает завершение всех страниц, а не утверждение бухгалтерской методики.

Метрика имеет `approval=demo`, `semantic_version=cash-receipts-v1`. Версия каталога вычисляется по хешу `$metadata`. Валюта ещё не подтверждена, поэтому единица — `ед. учёта`, а не предполагаемые рубли. Результат содержит источники, фильтры, версии, время получения, количество строк и страниц, предупреждение о несогласованной методике.

По умолчанию агент блокирует эту метрику. Для демонстрации предусмотрен явный доверенный флаг `ToolContext.allow_demo_metrics`; в worker он задаётся `ONEC_ALLOW_DEMO_METRICS=true`. Значение `approval=approved` не присваивается автоматически. Метрики со статусом `draft` остаются заблокированы даже в демонстрационном режиме.

## Область доступа и ограничения

1С используется только через GET и сервисную учётную запись. Настройка `ONEC_ORGANIZATION_IDS` ограничивает список организаций на стороне сервиса. Пустой список означает все организации, доступные этой учётной записи. Контекст агента дополнительно сужает область доступа.

По умолчанию: 100 строк на страницу, 5000 исходных денежных движений суммарно на принятый Query Plan, 2 попытки HTTP-запросов в секунду на процесс, не более 4 одновременных запросов к 1С и не более 60 секунд на операцию. Сетевые тайм-ауты подключения, чтения очередного фрагмента, записи и ожидания соединения задаются отдельно; без отдельных настроек наследуют `ODATA_TIMEOUT_SECONDS=15`. Общий срок включает ожидание очереди, паузы между попытками и все страницы. Лимит `ODATA_MAX_ROWS` публикуется в определении метрики как `max_rows_per_plan`. Runtime ведёт общий счётчик плана и передаёт исполнителю оставшийся бюджет через доверенный контекст и поле HTTP-запроса `max_rows`. Расчётные вызовы одного плана выполняются по очереди, даже если граф вызывает их параллельно. Повтор завершённого шага возвращает сохранённый результат без повторного расхода бюджета. После ошибки или отмены расчёта оставшийся бюджет закрывается, поскольку фактический объём уже прочитанных данных неизвестен.

Счётчик действует в пределах одного Runtime запроса; распределённое хранение бюджета между перезапусками worker не реализовано. При прямом обращении к `/v1/call` без плана действует лимит отдельного вызова. Загрузка подготовительных справочников имеет отдельный лимит `ODATA_MAX_ROWS` на справочник. Для обнаружения превышения OData может вернуть одну дополнительную контрольную строку; частичная сумма в этом случае не выдаётся.

Метаданные кэшируются отдельно на 900 секунд, организации и направления — на 60 секунд. Одновременные обновления объединяются локальными блокировками. Изменение хеша схемы инвалидирует кэш справочников. Контрагенты и денежные движения читаются по запросу. При ошибке обновления сервис сообщает ошибку, не подменяя её молча устаревшими данными. Распределённый кэш денежных выгрузок не реализован. Если рабочая база изменится между страницами, транзакционный снимок через этот интерфейс не гарантируется. Истечение общего времени запроса, включая bootstrap, возвращается с кодом `TIMEOUT`.

## Ошибки, повторы и наблюдаемость

Разрешён один дополнительный GET при `ConnectError` без ошибки сертификата, `ConnectTimeout` либо HTTP 429/502/503/504. Пауза нарастает с небольшим случайным сдвигом; учитывается `Retry-After`. Повтор не начинается, если пауза не помещается в общий срок. `ReadTimeout`, `WriteTimeout`, `PoolTimeout`, ошибки сертификата, авторизации, аргументов и схемы автоматически не повторяются. Каждая повторная попытка проходит тот же ограничитель частоты. Данные повторно прочитанной страницы учитываются в сумме один раз.

Журнал `onec_data` содержит JSON-события `odata_request`, `odata_retry`, `odata_deadline`, `metadata_refreshed`, `data_request`. Для сетевого запроса сохраняются источник, номер страницы, номер попытки, длительность, HTTP-статус и тип/этап ошибки. Заголовки авторизации, URL с параметрами, тексты ответов 1С и строки базы не журналируются. `X-Request-ID` связывает адаптер, HTTP-ответ, ошибку и журнал сервиса. При запуске через Uvicorn события выводятся в stderr.

Публичный код `TIMEOUT` сохранён. В `error.details` добавляются безопасные `stage`, `error_type`, `attempts`, `upstream_status`, `request_id`. HTTP-статусы сервиса: тайм-аут — 504, отсутствие соединения — 503, ошибка ответа/авторизации 1С — 502, отказ области доступа — 403. Флаг `retryable` передаётся независимо от HTTP-статуса, поэтому ошибка учётной записи не становится временной из-за статуса 502. В `stats` расчёта добавлены `duration_ms`, `upstream_requests`, `upstream_retries`, `upstream_ms`.

Настройки:

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `ODATA_TIMEOUT_SECONDS` | 15 | Резервный сетевой тайм-аут |
| `ODATA_CONNECT_TIMEOUT_SECONDS`, `ODATA_READ_TIMEOUT_SECONDS`, `ODATA_WRITE_TIMEOUT_SECONDS`, `ODATA_POOL_TIMEOUT_SECONDS` | Наследуют резервный | Отдельные этапы сети |
| `ODATA_MAX_RETRIES` | 1 | Дополнительные попытки, максимум 3 |
| `ODATA_RETRY_BACKOFF_SECONDS` | 0.5 | Базовая пауза повтора |
| `ODATA_MAX_CONNECTIONS` | 4 | Параллельные запросы и размер пула |
| `ONEC_METADATA_TTL_SECONDS` | 900 | Кэш схемы |
| `ONEC_CATALOG_TTL_SECONDS` | 60 | Кэш организаций и направлений |
| `ONEC_DIMENSION_SEARCH_LIMIT` | 20 | Максимум показанных кандидатов |

Ограничитель частоты и пул действуют на процесс. Для нескольких экземпляров сервиса потребуется общий ограничитель нагрузки.

## Конструктор запросов для AI

`services/onec_data/query.py` определяет `EntityQuery`: источник, выбираемые поля, типизированные условия AND/OR, сортировка, лимит, поле суммы и группировки. Компилятор проверяет источник и поля по разрешённому `$metadata`, сериализует литералы OData v3, экранирует апострофы и дополняет сортировку ключами. Поля суммы и группировок включаются в проекцию для расчётов на стороне сервиса; `$apply` OData v4 не используется.

Пример внутреннего плана:

```json
{
  "entity_name": "Catalog_Контрагенты",
  "select": ["Ref_Key", "Description"],
  "filters": [
    {"field": "DeletionMark", "value": false},
    {"field": "Description", "operator": "contains", "value": "демо"}
  ],
  "limit": 20
}
```

Сценарий поступлений и поиск справочника уже используют этот конструктор. `get_entity_schema` возвращает его JSON Schema. Это основа расширения NL2OData: существующий агент по-прежнему передаёт согласованные инструменты и параметры в `QueryPlan`. Произвольного исполнения плана из LLM через отдельный HTTP-метод нет. Новая бизнес-метрика требует описания источников, обязательных фильтров, области доступа и методики; численно по-прежнему подключены только поступления.

На предоставленной базе проверены `substringof('текст',Description)`, поиск в разных регистрах и литерал с апострофом. Вложенный `substringof('текст',tolower(Description))` возвращает HTTP 400 с ошибкой типа аргумента и не используется. При подключении другой конфигурации поведение строкового поиска следует проверить отдельно.

## Повторные замеры подключения

```bash
.venv/bin/python scripts/diagnose_onec.py --attempts 5 --interval 5 --resolve-ip 176.108.255.199
```

Команда читает настройки из окружения или необязательного `.env`; пароль при необходимости вводится скрыто. Выполняются ограниченные GET к `$metadata`, одной строке справочника и локальному API, в том числе сравнение DNS/заданного IP и прямой HTTPX-запрос. Версия сервиса, этапы соединения и коды ошибок сохраняются в `runs/diagnostics/connection-*.jsonl` без паролей и данных базы. Флаг `--no-auth` проверяет только сеть: HTTP 401 в этом режиме ожидаем. Для сквозной проверки `scripts/check_onec.py --allow-demo` также не нужны `.env` и ключ OpenRouter; если `.env` существует, скрипт подхватит внутренний токен.

## Подключение worker

В окружении worker задайте:

```dotenv
ANALYTICS_BACKEND=onec
ONEC_DATA_URL=http://127.0.0.1:8011
ONEC_ALLOW_DEMO_METRICS=true
```

Для новых веб-чатов задайте на стороне API `CHAT_ORGANIZATION_ID` с разрешённым UUID из bootstrap.
Веб-чаты сохраняют назначенную организацию при создании. После смены настройки создайте новый чат.
Ограничьте доступ к инсталляции с реальной 1С пользователями, которым разрешены данные этой организации.
Ключ OpenRouter не нужен для проверки `scripts/check_onec.py`. Обычный worker использует настроенную модель проекта, поэтому использование внешней модели с реальными данными нужно согласовать отдельно.

Для Docker заполните параметры 1С, `ONEC_DATA_TOKEN` и `CHAT_ORGANIZATION_ID` в локальном `.env`, затем:

```bash
ANALYTICS_BACKEND=onec ONEC_ALLOW_DEMO_METRICS=true docker compose --profile onec up --build
```

В Docker адрес сервиса передаётся worker автоматически как `http://onec-data:8011`. Сам сервис слушает порт 8011 внутри сети, публикация на хост ограничена localhost. Профиль `onec` нужен при выборе реального источника.

## Контрольный результат

При проверке 15.11.2026 за `[2025-01-01, 2025-02-01)` по направлению «Разработка ПО»:

| Организация | Движения | Итог |
|---|---:|---:|
| ООО «Демо-Софт» | 13 | 5 988 658.00 ед. учёта |
| ООО «Демо-Торг» | 0 | Нет данных, `total=null` |

Значения совпали при вызове через HTTP-адаптер и через граф. Эталонный отчёт и правила валюты/авансов ещё должен подтвердить заказчик.

Автоматические проверки: `.venv/bin/python -m pytest -q`. Docker-конфигурация проверяется `docker compose --profile onec config --quiet`. Полноценный запуск контейнеров требует работающего Docker Engine.
